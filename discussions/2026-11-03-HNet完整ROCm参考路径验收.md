# H-Net 完整 ROCm 参考路径验收

日期：2026-11-03，America/Los_Angeles。接续用户授权的本机 ROCm 适配。
起点 `0073a2d` 数据分支干净、fetch 后与 origin 差异 0/0；建立专用 `codex/hnet-rocm-8060s`，
保留旧数据分支、样例及 CPU 环境，不合 main。[实现与全部命令](../experiments/hnet_rocm/README.md)。

## 对象、尺度和验收定义

对象是官方原版 `cartesia-ai/hnet_2stage_L` 的 874,315,264 参数模型，不是本项目尚待训练的 v1.2 B/F。
旧 2026-11-02 实验只执行 70M 编码／路由参数；不能用其观测当成完整 ROCm 成功。
本次逐项检查硬件和软件、真实 HIP 张量、完整主干与解码、全部梯度、一次优化器步、CPU 数值对照。
“GPU 参考路径通过”与“原 fused 算子已移植”“缓存生成完成”“正式训练可长期运行”分别验收。

## 实际环境与版本资料修订

只读核对 Windows 11 Pro build 26200、Ryzen AI Max+395 16C/32T、Radeon 8060S、128GB 级物理内存；
驱动 32.0.31032.1003。旧 torch 为 2.8.0+cpu，WSL 未安装。新 `.venv-hnet-rocm` 使用官方
torch 2.9.1+rocm7.2.1／HIP 7.2.53211／Python 3.12.14。SDK clang22 与 hipcc 的 --version 实际运行通过。
实际 HIP 设备 gfx1151、可访问总内存约 83.95GB；CIM AdapterRAM 的 32-bit 报数不作可用显存判断。

首轮 MSVCP140 搜索路径缺失：AMD DLL 本身存在，经 PE import 检查定位，进程内加载已有
Microsoft 签名有效的 Codex runtime DLL 解决。沙箱内分配曾发生 HIP 0xC0000005，允许设备访问的
同形状 randn256／matmul／反向通过；未据此宣称查明驱动内部故障。未关闭安全设置。

资料核查补充后明确：旧 Radeon/Ryzen latest 文档仅覆盖到 7.2.1，不能当最新统一支持表。
已核对[统一 10.1.0 矩阵](https://rocm.docs.amd.com/en/latest/compatibility/compatibility-matrix.html)、
[PyTorch 安装页](https://rocm.docs.amd.com/projects/ai-ecosystem/en/latest/frameworks/pytorch/install.html)
和实际 Windows cp312 wheel HEAD。新版对应 Adrenalin 26.10.41.05，
[Driver Store 32.0.31041.5005](https://www.amd.com/en/resources/support-articles/release-notes/RN-RAD-ROCM-10-01.html)，
本机版本较旧，因此保留当前已过全流程的 7.2.1，10.1 未安装／未运行，不修改驱动。
7.2.1 官方限制中的“无训练支持”只代表该版本的支持边界；本次实际单进程 backward/SGD 成功是
实验结果，不等于官方生产训练保证，也不将旧限制推广到当前全部 Windows 版本。

## 实现与实测事实

新实现保留完整检查点所有参数名与原递归结构。Mamba SSD、causal conv1d、SDPA math、
RMSNorm／SwiGLU 用可微 PyTorch HIP，硬路由与 STE、两级 dechunk、细粒度残差和 padding 保留。
原 Mamba／causal-conv1d／FlashAttention／Triton 扩展未安装、未编译和执行，原生 fused 状态 not-run，
不是已证明不可用。官方 HNet.forward／router／chunk／STE 控制图通过固定 hash AST 独立执行作组合对照，
其 Isotropic/dechunk 仍为参考原语，不能冒充原 fused 图。

正式输入原文为 50 个 ASCII 字节，前 49 字节作输入、后 49 字节作 next-byte 标签，无 BOS/EOS：
`The red box holds 17 coins. Keep it by the window.`。层级 **49→21→8**，内层 T26、两级 decoder
与 head 全部执行，logits [49,256] 有限。328 个参数张量全部有有限非零 GPU 梯度，无冻结；
一次 SGD（lr1e-5，momentum .9，foreach false）生成覆盖全部参数的 GPU 状态，抽查 head、两 router、
内层 attention、两 decoder 均更新。FP32 EMA loss 1.34195876，峰值 allocated 10.93GB。
另按原 forward BF16 dechunk 转换参考运行全流程，loss 1.34148467，同样通过。

5 类算子 GPU FP32 前向／VJP 对照独立 CPU FP64 公式，加独立 STE 检查，均通过，最大 VJP 差约4.06e-6。
完整模型同权重同 FP32 参数的 CPU serial SSD 对 GPU block SSD：logits 最大差4.673e-5、平均4.862e-6，
loss差2.384e-7，两级路由一致，预先固定 atol=rtol=1e-3。BF16 dechunk 方式最大差.002062，
混合绝对／相对容差也通过。样例无近 .5 路由点，不能外推任意输入边界必定一致。
原始 checkpoint 经全文件重算 SHA-256 与锁定值一致，没有写回训练后权重。

完整 GPU 前向约7.31s、反向1.46s、优化器1.00s；后运行的 BF16 dechunk 试验2.21／1.47／1.11s，
CPU serial前向.41s。单次短序列、不同缓存／初始化影响，不是公平速度基准，不作 GPU 加速主张。

## 反例、未验证项与下一步

设备枚举成功而沙箱内分配崩溃，是不能以 wheel 导入／枚举代替实际算子的直接反例。
两种 dechunk 方式都有数值精度差，BF16 最大误差高于 FP32；路由恰近阈值时可能改变离散结构。
当前只验证 batch1、短前缀、单进程、FP32 参数及一步优化；没有完整长训练／多卡／生产性能结果。

官方推理缓存、SSM／conv 状态、attention KV、router/dechunk cache 与 GenerationMixin 未实现验收；
本次通过的是 full-prefix 参考推理与训练步，不是高效缓存生成。后续若需要原生 fused／高效推理，
应分别建立 kernel forward/gradient parity 和 cache-step/prefill parity；若升级10.1，先具体核对适用驱动再确认系统变更。
当前已通过项不依赖用户改系统。全程无付费租机、大数据下载、驱动／WSL／安全设置修改、重启、KVM或进程干预。
